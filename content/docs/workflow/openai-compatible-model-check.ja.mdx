モデルの認証情報を保存できることと、ワークフローから正しい結果を受け取れることは、別の確認項目です。検索、ツール、ループを追加する前に、小さな診断用ワークフローで問題のある層を特定しましょう。

**対象範囲：**Dify の OpenAI-API-compatible **モデルプロバイダー**プラグインを使う、テキストのみの Workflow です。2026 年 11 月 6 日に公開ドキュメントとプラグインのソースを確認しました。この寄稿のために Dify インスタンスや有料モデル API を実行してはいません。以下の 2 件の入力は提案する受け入れテストであり、実測結果ではありません。インストール済みの Dify とプラグインのバージョンによって、表示名や設定項目が異なる場合があります。

## 1. リクエストの向きを整理する

| 目的 | リクエストの向き | 認証情報の発行元 |
| --- | --- | --- |
| Dify の LLM ノードでモデルを利用する | Dify → モデルサービス | そのモデルサービス |
| 自分のバックエンドから公開済みの Dify アプリを呼ぶ | 自分のバックエンド → Dify アプリ | その Dify アプリ |

ここでは 1 行目を扱います。Dify アプリのキーをモデルサービスのキーの代わりには使えません。秘密情報はプロバイダーの認証情報欄に保存し、プロンプトや共有する調査資料には入れないでください。[モデルプロバイダー](https://docs.dify.ai/en/cloud/use-dify/workspace/model-providers)と [Dify API の認証](https://docs.dify.ai/en/api-reference/guides/get-started)も参照してください。

現在の Dify Cloud ドキュメントでは、設定場所は **Integrations → Model Provider** です。管理にはワークスペースのオーナーまたは管理者の権限が必要です。利用中のバージョンで対応する設定を確認してください。選ぶのはモデルプロバイダープラグインです。名前が似ているツールやアプリアダプターは、逆向きの接続を扱っている場合があります。

保存前に、キーを含めない設定メモを作ります。

| 項目 | 確認すること |
| --- | --- |
| プラグイン | 正確な名前とインストール済みバージョン |
| モデル種別 | このテキスト生成の例では LLM |
| モデル名 | 宣伝上の名称ではなく、サービスが受け付ける ID |
| `display_name` | 画面上のラベル。変更しても上流モデルの変更を証明しない |
| `endpoint_model_name` | 設定されている場合は上流モデルの上書き値も確認 |
| `endpoint_url` | プラグインとサービスが要求する API ベース URL |
| API タイプ / モード | エンドポイントのプロトコルと一致させる。「chat」という表示だけで判断しない |
| 機能と上限 | フォームの初期値ではなく、そのモデルと経路が対応する値 |

確認した[プロバイダーの定義](https://github.com/langgenius/dify-official-plugins/blob/5139339f0b3632494f4e15476c56ae2f82a1e7d8/models/openai_api_compatible/provider/openai_api_compatible.yaml)では、表示名、上流モデルの上書き、API タイプ、モデルモードが分かれています。古いプラグインには一部の項目がない場合があります。

サービスが `https://model.example/v1` を API ベース URL として指定しているなら、対応する欄にはそのベース URL を入力します。完全なリクエスト例に `https://model.example/v1/chat/completions` が載っていても、操作パスまでそのまま貼り付けないでください。逆に、すべてのサービスへ機械的に `/v1` を追加するのも避けます。サービスが指定するベース URL と、プラグインによるパスの組み立てを両方確認します。`model.example` は説明用のホスト名であり、呼び出すサービスではありません。

**認証情報の保存や検証は、モデルへのリクエストと課金を発生させる場合があります。**確認した[プラグイン実装](https://github.com/langgenius/dify-official-plugins/blob/5139339f0b3632494f4e15476c56ae2f82a1e7d8/models/openai_api_compatible/models/llm/llm.py)にも検証用リクエストがあります。実行前に、接続先、料金、キーの利用権限を確認してください。認証情報の検証成功だけでは、ワークフロー全体、長い回答、ストリーミング全体の成功は確認できません。

## 2. 入力と出力を明示した 1 本の経路を作る

本番アプリとは別に、新しい診断用 Workflow を作ります。

```text
User Input (source_text) → LLM → Output (result_text)
```

1. 入力ノードに必須のテキスト変数 `source_text` を追加します。このノードを **Start** と呼ぶバージョンもあります。
2. **LLM** ノードで、設定したプロバイダーとモデルを明示的に選択します。この例では Chat Completions に対応したチャットモデルと経路を使い、`mode: chat` を選びます。プラグインに API タイプの項目がある場合は `chat_completions` を指定します。Model 欄が LLM 環境変数を参照している場合は、その変数の選択内容を確認します。ワークスペースの既定モデルを変更するだけでは、このノードの確認にはなりません。
3. System の指示には次を使います。

   ```text
   Read the input. Return only its order label and shipping day, separated by |.
   Copy those two values from the input. Do not invent values or add commentary.
   ```

4. User プロンプトには、Dify の変数セレクターから**入力ノードの source_text** を挿入します。エディターに表示された変数参照を確認してください。`source_text` という通常の文字列を入力するだけでは参照になりません。別のワークフローからコピーしたプレースホルダーが、別ノードを指す場合もあります。
5. **Output** に `result_text` を作り、その値として LLM ノードの **text** 出力を選びます。期待する回答を固定値として入力しないでください。

[LLM ノードのドキュメント](https://docs.dify.ai/en/cloud/use-dify/nodes/llm)には、プロンプト変数とモデル選択の説明があります。現在の [Output ノードのドキュメント](https://docs.dify.ai/en/cloud/use-dify/nodes/output)によると、Output がない分岐も実行できますが、呼び出し元へデータを返しません。旧バージョンでは **End** という名前です。Chatflow は **Answer** を使うので、アプリ種別をまたいで最後のノードをそのままコピーしないでください。

## 3. 実行前に 2 件の受け入れテストを決める

以下は合成入力と期待内容であり、モデルのベンチマークではありません。

| ケース | `source_text` | `result_text` の期待内容 |
| --- | --- | --- |
| A | `Order ALPHA17 ships Wednesday.` | `ALPHA17 \| Wednesday` |
| B | `Order BETA28 ships Friday.` | `BETA28 \| Friday` |

区切り文字の前後の空白は許容しますが、注文ラベルと発送曜日が正しく、余分な説明がないことを確認します。2 件目は、1 件目だけでは見つからない古い入力や固定回答の問題を検出するためのものです。失敗しても、その時点でプロバイダーが原因とは断定できません。

実行の許可と費用を確認した後、A と B を別々の Workflow 実行として試します。各実行の [Run History](https://docs.dify.ai/en/cloud/use-dify/debug/history-and-logs)を開き、トレースと該当ノードの **Last run** を調べます。

- 入力ノードは新しい文字列を受け取ったか。
- 意図した LLM ノードが実行され、実際のプロンプトに新しい文字列が含まれたか。
- その実行で選択されたプロバイダーとモデルは正しいか。
- LLM が返したテキストと、Output が返した内容は何か。
- 正常終了したのか、それともエラー経路やフォールバックが画面の結果を返したのか。

B でも `ALPHA17` が返るなら、まず入力とプロンプトの参照を確認します。LLM の出力が正しいのに返却結果が空なら、Output の対応付けと実行された分岐を確認します。両方とも利用可能なモデル応答を受け取る前に失敗するなら、プロバイダーへのリクエストを調べます。これは問題の層を絞る手順であり、モデル全般の精度を証明するものではありません。

## 4. 失敗した層の証拠から調べる

| 観察した現象 | 最初に確認する証拠 | 避けるべき思い込み |
| --- | --- | --- |
| 401 / 403 | 応答したサーバー、秘密情報を除いたエラー本文、キーの発行元と権限 | 認証エラーはすべて Dify アプリのキーを交換すれば直る |
| 404 | 実際のパス、ベース URL、API タイプ、モデルのエラー文 | 404 は必ずモデル名の誤り |
| 400 / 未対応パラメーター | エラーの項目とプロトコル。未対応の任意設定を 1 つずつ外す | 設定を有効にすれば上流も対応する |
| 429 | プロバイダーのエラー詳細、アカウントやレート制限の状態 | 直ちに繰り返し再試行しても無料で有効 |
| タイムアウト / TLS / 接続エラー | 接続先ホストと、実際の実行環境からの到達性 | ブラウザーで開けばワークフローからも到達できる |
| LLM のテキストは正しいが返却結果が空 | Output の参照元、実行経路、最終結果 | 認証情報を保存できれば出力の配線も正しい |
| 認証チェックは成功するが大きなタスクは失敗 | 失敗ノード、要求サイズ、パラメーター、完了状態 | 短い検証要求で全機能と応答長を確認できる |

ステータスコードは手掛かりであり、診断結果ではありません。テストを「成功」させるために証明書検証を無効化したり、Issue に秘密情報を貼ったりしないでください。タイムアウト後の結果が不明な場合は、再試行の前に元の実行とプロバイダーの使用記録を確認します。ワークフローに外部への書き込みが含まれる場合は、特に重要です。

## 5. 秘密情報を除いた実行メモを残す

次のシートをコピーし、観察した事実で埋めます。実施していない確認は `not run` のままにして、成功と事前記入しないでください。

```text
Date/time and timezone:
Dify version / Cloud:
Provider plugin and version:
API base hostname/path (no query secrets):
Protocol and model ID / override:
Case: A / B
Run ID:
Input observed at LLM:
LLM output observed:
Output result observed:
Final run status:
Error source/status/request ID, if present:
Actual cost: unknown / checked in provider billing
Next change (one at a time):
```

診断用ワークフローが通った後、検索、ツール、分岐を 1 つずつ追加して必要な確認を繰り返します。公開アプリは実際の利用経路から別途検証してください。エディター内のテストだけを本番の検証結果として扱わないようにします。
